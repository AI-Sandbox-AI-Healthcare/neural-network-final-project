Can AI Predict Chronic Pain from Clinical Records?

This project benchmarks seven machine learning models on a binary classification task: given a synthetic patient’s clinical history — demographics, vitals, medications, and encounter notes — predict whether they have a chronic pain condition. We compare models ranging from a simple logistic regression to a fine-tuned clinical BERT transformer, across 30 independent random-seed iterations on 12,352 synthetic patients.

🏥
Clinical Context
Chronic pain affects roughly 20% of US adults and drives enormous healthcare costs. Identifying patients early from routine EHR records could help clinicians prioritize care before conditions worsen.
🎯
Research Question
Which model architecture — from simple tabular baselines to deep sequence models — gives the best trade-off between predictive performance and computational cost on this patient classification task?
🔬
Scientific Rigor
All models share the same stratified train/validation split per iteration. Results are averaged across 30 runs with different random seeds, giving stable, comparable estimates with reduced variance.

Feature Engineering Pipeline
Raw Synthea CSVs go through five processing stages before reaching the models. Each stage adds a new type of signal. Click any stage to learn more.
Stage 0 — Raw Input
6 Synthea CSV Files
patients.csv • conditions.csv • encounters.csv • medications.csv • procedures.csv • observations.csv
↓
Stage 1 — Structured Extraction
Patient Feature Vector
Join all six tables on patient ID. Aggregate per-patient: count unique medications, total encounters, average condition duration, latest vitals from observations, pain severity score. Label patients as pain=1 if any active pain condition exists.
Random Forest XGBoost LSTM GRU Transformer ClinicalBERT
↓
Stage 2 — Text Feature Extraction
TF-IDF Drug Frequencies + LDA Topics
Concatenate all medication names and descriptions per patient into a single “medication note.” Run TF-IDF to extract 12 key drug term frequencies (opioids, anti-inflammatories, etc.). Fit a 5-topic LDA model to discover latent medication usage patterns across the population.
TF-IDF LogReg Random Forest XGBoost
Stage 2b — Dimensionality Reduction
PCA & UMAP
Compress the full TF-IDF feature space into 2 PCA components and 2 UMAP components. These low-dimensional embeddings capture the global structure of medication patterns and are appended to the structured feature vector.
RF XGB
↓
Stage 3 — Visit Sequences
Time-Ordered Encounter Arrays
For each patient, sort encounters chronologically. For each encounter, build a feature vector (vitals, medications dispensed, procedures done). Pad or truncate to a fixed length. This 2-D array (visits × features) is the input to sequence models — each time-step is one clinical visit.
LSTM GRU Transformer
Stage 3b — BERT Tokenization
ClinicalBERT Embeddings
Tokenize the medication note sequence using the ClinicalBERT WordPiece tokenizer (max 512 tokens). Pre-compute the [CLS] embedding (768-dim) for every patient — this step runs once and is cached, saving GPU time during training.
ClinicalBERT
↓
Stage 4 — Output
Model-Specific Feature Sets Ready for Training
Each model type receives the representation that best fits its architecture: flat 44-dim vectors for tree models, 2-D sequence arrays for RNNs/Transformers, or 768-dim BERT embeddings fused with structured features for ClinicalBERT.
Why Medication Text?
🔑 Key Signal
Pain medications (opioids, anti-inflammatories, gabapentin) are often the earliest documented evidence of chronic pain in the EHR — sometimes appearing months before a formal diagnosis code. TF-IDF medication frequencies capture this signal even when structured pain severity scores are missing or unreported.
⚠️ Leakage Risk
We deliberately excluded the raw condition text (diagnosis codes and descriptions) because the pain label was created from that text directly — using it as a feature would give models a “cheat sheet” and produce artificially perfect AUC scores. Medication text avoids this because it is independently generated from prescribing behavior.

Core ML Practice
Reproducibility

A model that reports F1 0.770 from a single run may have simply gotten lucky with its random train/validation split. A model that reports F1 0.741 ± 0.007 across 30 independent runs is telling you something you can trust. Reproducibility is the difference between a result and a finding.

🎲
Random Seed
Controls how data is split and how models initialize. Different seeds = different results.
📊
Standard Deviation
How much results vary across runs. Low std = stable model. High std = sensitive to split luck.
🔁
30 Iterations
Each iteration uses a fresh random seed, shared across all 7 models so comparisons are fair.

The core lesson
1
Never report a single run. A lucky split can inflate F1 by 0.01–0.02 over the true value.
2
Share your random seed. Anyone re-running your code should get the same number.
3
Report mean ± std. The spread tells readers how confident they should be in your result.
4
Use shared splits. All 7 models here use the same 30 train/val splits — that's why their comparisons are fair.

The AUC Convergence Problem

Seven models — from a 5-line logistic regression to 110M-parameter BERT — all land at AUC 0.826–0.832, a spread of 0.006. The per-model standard deviation across 30 iterations is ±0.007, meaning these models are statistically indistinguishable.

Propose a specific mechanism that explains this performance ceiling. Is it a data limitation, a label quality problem (chronic pain is subjectively diagnosed), or a fundamental ambiguity in the EHR signal? How would you empirically test your hypothesis — without collecting new data?

The Efficiency Paradox

Random Forest: $0 · 5 sec · AUC 0.830 · Precision 0.761.
ClinicalBERT: $0.05 · 49 sec · AUC 0.832 · Precision 0.829.
The AUC gap is noise. The precision gap is real.

Design two clinical deployment scenarios — one where ClinicalBERT's precision justifies its 10× cost, and one where Random Forest is the only ethical choice. What specific factors in each scenario drive the decision? Your answer must cite both metrics and the computational comparison from this UI.

The Reproducibility Trap

Across 30 independent train/val splits, ClinicalBERT's AUC ranges from 0.816 to 0.846 — a spread of 0.030. Random Forest spans 0.810 to 0.845. No model is consistently "the best" across every run. The winner changes depending on which split you happened to draw.

A colleague shows you a paper claiming Model A outperforms Model B by 0.015 AUC on a single held-out split. Using evidence from the Reproducibility tab, construct a specific statistical argument for why this claim may not hold. What minimum experimental design — number of runs, split strategy, and reporting standard — would you require before accepting such a comparison as valid? Justify each requirement.

04
The Medication Text Paradox

TF-IDF LogReg (medication text only) achieves AUC 0.775 — worst of seven. Random Forest (zero text features) achieves AUC 0.830. Yet medication-derived features (tfidf_opioid, topic_1, pca_1…) rank among the top predictors in the Random Forest importance chart.

Explain the contradiction. Why does medication text help Random Forest but not TF-IDF LogReg as a standalone model? What does this reveal about individual feature value vs. feature value in context? Follow-up: if forced to drop exactly half the features (22 of 45), which would you keep and why?
